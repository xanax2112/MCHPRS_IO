### 1.1 电路测试分类

| 分类 | 含义 | 代表 |
| --- | --- | --- |
| 时序精确（无时钟 / 有时钟，同一规则） | 给定元件延迟；每组只允许 1 条 `OUTPUT`（多条=毛刺→失败）；`OUTPUT` tick 必须等于「输入生效 tick + 延迟 − 1」；该 tick 上的值正确即通过。有时钟组 `INPUT` 脉冲一次 `clk`，输出只在上升沿推送，判定不变 | xor（PY-002） |
| 流水时序精确 | 仅 `/tick seq`；给定输入间隔（≥2t）与输出延迟；连续灌入向量，判定相邻输出间隔 == 输入间隔且每个值正确 | 待定 |
| 无时序正确性 | 只写输入，等一段时间，中间 `OUTPUT` 全丢弃，`POUT` 查一次，值对即通过；**不判 tick** | xor（PY-003，示例） |

其余分类 ⏳ 待用户说明，未登记前不自行假设。

**PY-002 `xor.py`（🚧 已写码，未验收）**

- 需求（用户 2026-11-02 确认）：输入 8×2（16 位，高 8 位 | 低 8 位），输出 8 位；
  期望 `xor_out == 高 8 位 ^ 低 8 位`；**普通模式，`INPUT` 后等 `OUTPUT`**。
- 电路分类：**无时钟时序精确**（用户 2026-11-02 分类，见 §1.1）。
- 延迟（用户 2026-11-02 修正）：设计延迟 **1t**；按项目写法「真实延迟 = 输出采样 tick − 输入生效 tick + 1」，
  脚本应算出的延迟是 **0t**，即断言 `输出 tick − 输入 tick == 0`。**原先按 +1 写的断言已作废。**
- 判定（用户 2026-11-02 完整定义，覆盖此前所有写法）：
  - 给定元件**延迟**（tick），xor 为 1t；
  - 发 `INPUT`，记录**输入生效 tick**；
  - **每组只允许收到 1 条 `OUTPUT`**；收到多条 → 视为**毛刺**，该组失败；
  - `OUTPUT` 的 tick 必须等于正确延迟 tick（项目写法换算：`输出 tick = 输入 tick + 延迟 − 1`）；
  - 在该 tick 上检查值，等于 `A ^ B` → 通过。
- **有时钟组并入同一判定**（用户 2026-11-02 定）：`INPUT` 会脉冲一次 `clk`，输出组只在上升沿推送；
  延迟、毛刺、tick 规则与无时钟组完全一致，不另立条目。
- 参数（用户 2026-11-02：**全部写在代码配置区**，不走命令行）：`DELAY` 元件延迟（xor = 1）；
  `GLITCH_WAIT` 毛刺观测窗口；0 条 `OUTPUT` → 先用 `POUT` 确认再判。
- 热身（用户 2026-11-02 先要求、同日取消）：**已移除**，不做任何预热；首组若值未变化，走 `POUT` 确认分支。
- 实现：`timing.py`（旧 `xor.py` 已按用户 2026-11-02 指令删除，功能并入通用时序精确测试）。
- 实测（2026-11-02，`betterio = true`，rtps 5000）：**65535 通过 / 1 失败**，耗时 324.8s；
  65535 个有效样本的 tick 差**全为 0**（即项目写法的 1t）。
- 那 1 条失败已定性：`A=0x80 B=0x00`（期望 0x80），前一组 `A=0x7F B=0xFF` 输出也是 0x80
  → **值不变、无推送**，是遍历顺序造成的假失败，**不是服务器问题**。
- 修复：内层改蛇形遍历（相邻组只变一位，输出必变），**待重跑确认**。

**PY-003 无时序正确性测试（📝 已登记，待写码指令）**

- 流程（以异或门为例）：

**PY-008 pipeline 毛刺诊断（📝 已定，待写码；2026-11-05）**

- 用户定义：某批里出现的、不属于该批任何一组 `expect_tick` 的推送就是"预期之外的多余输出"。
  把两个信号彻底分开：预期 tick 没有输出 = 漏推送；非预期 tick 有输出 = 毛刺。
- 打印（用户 2026-11-05 确认要三条）：每条毛刺按 tick 升序打
  ① 前一个预期 tick 的期望值与该 tick 实际推送值 ② 毛刺本身 tick 与实际值 ③ 后一个预期 tick 的期望值与实际值；
  边界（位于该批第一个预期之前 / 最后一个预期之后）只打存在的一侧并标注"批次边界"。
- 若毛刺同时让某组判错（同 tick 多条 / 值不符 / 无输出），错误信息一起打印并附带同样三条明细。
- 明细上限沿用 `MAX_DETAIL = 20`，超出只报总数；有毛刺即整轮失败；汇总分开报 `推送 N 条，毛刺 M 条，漏推送 K 条`。

**PY-018 `wait_seconds` 同时被当成控制往返超时，50 ms 太紧 → `预约未被确认：`（空错误串）（🐞 已登记，未写码；2026-11-05 22:45 用户实测）**

- 现象：pipeline 模式一连三次都停在同一处，日志只有两行有效内容：
  ```
  已连接：协议 0.6.1-alpha，当前 tick 196666
  预约未被确认：
  ```
- 定位（读码可得）：`预约未被确认：%s` 只由 `run_pipeline` 的 `except TimeoutError` 打印；
  `reserve_batch` 里会抛 `TimeoutError` 的地方有**三处，其中两处都没有消息**：
  1. `tick_now()` → `expect("NOW")` → `_recv_line()` 的 socket 超时 → **无消息**；
  2. `expect_batch_ok()` 里 `_recv_line()` 的 socket 超时 → **无消息**（只有"条数不够"那条分支带消息）；
  3. `send()` 的 `sendall` 超时 → 无消息（`socket.timeout` 就是 `TimeoutError`）。
  所以仅凭空错误串**无法区分**是"第一条 TICK NOW 没回"还是"32768 行批次灌完后等确认时超时"。
- 时间账（用日志 mtime 反推，不是猜）：
  - `pipeline_20261105_224536_190.log` 开始 22:45:36、结束 42（6 s）——**成功**跑完第 1 批
    （`RADV 4.140s -> 7916 组/s`），说明 32768 行的批量路径本身能通；
  - `pipeline_20261105_224544_316.log` 开始 44、结束 48（**约 4 s**）；
  - `pipeline_20261105_224553_457.log` 开始 53、结束 55（**约 2 s**）；
  - 服务端 "became the /tick seq exclusive script" 分别出现在 36.35 / 46.80 / 53.48，
    即第二次连接本身等了约 2.4 s 才被登记（22:45:33 界面已 onPause，App 进后台被限流/挂起）。
  → 失败那两次**不是 50 ms 到期就立刻返回**，而是整个进程被系统挂起/降频了 1~2 s；
  50 ms 的控制超时在这种环境下必然误判。
- 根因：PY-012/PY-013 把 `wait_seconds`（0.05）同时当成了 pipeline 的控制往返超时。
  以前这里用的是 5.0，50 ms 对"连接后第一次往返"太紧：实测那次客户端从启动到连上花了约 2.8 s
  （日志时间 22:45:44，服务端 "became exclusive" 是 22:45:46.8），说明当时手机端调度很慢
  （App 切到后台被限流）——一次 `TICK NOW` 超过 50 ms 就必失败。
- 服务端侧无可疑记录：三条 `became the /tick seq exclusive script`（22:45:36 / 46 / 53）都正常，
  之后 22:45:58 才是用户手动停止，没有 panic、没有 ERR。
- 服务端日志：`/storage/emulated/0/termux/MCHPRS_IO/logs/app.log`、
  `logs/mchprs.log.2026-11-05`；客户端日志 `python/log/pipeline_20261105_224544_316.log`。
- 建议修法（待写码，三条都做才彻底）：
  1. **控制往返单独给下限**：`HELLO` / `TICK NOW` / POUT 用 `max(2.0, wait_seconds)`，
     批次空闲超时仍用 `wait_seconds`；
  2. **发起批量写入前把 socket 超时调大**（`sendall` 不该继承上一条读留下的 50 ms）；
  3. `expect()` / `expect_batch_ok()` 把 socket 超时包成带阶段名的异常
     （`"等待 NOW 超时（0.05s）"` / `"等预约确认超时（已收 n/32768）"`），别再出现空错误串。
- 附带观察：成功那两次的日志里第 1 批前 20 组左右仍报错（40~51 个失败），与 BUG-038 的冷启动现象一致。
- 关联：PY-012（timeout/collect 合并）、PY-013（wait_seconds 全局唯一）、PY-014（空闲超时）。
